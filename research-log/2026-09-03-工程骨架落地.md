# 2026-09-03 · 工程骨架落地：从「文档集」到「有工程」

## 问题

用户指令：「推进到鸿蒙基座完成」。

但已知卡点是 Command Line Tools 需要华为账号登录 + 动态验证码，Agent 代办不了。
所以真问题变成两个：

1. **在没有 CLT 的前提下，最远能推到哪一步？**
2. 剩下不能推的部分，边界到底在哪、是什么性质的阻塞？

结论先行：**推到了「有一个官方模板生成的真实工程 + 混合容器代码写完」，但一行都没编译过。**
「鸿蒙基座完成」按「能编译、能装、能跑」的定义**没有完成**，且剩下的部分不是靠更努力能绕过的。

## 检索路径与实测

这次几乎不查文档，全部是对本机 DevEco CLI 包的实测与反读。

| 动作 | 结果 |
| --- | --- |
| 无 CLT 直接 `devecocli create` | `Error: Invalid DEVECO_CLI_CLT_PATH: ...` |
| 造一个只含 `version.txt` 的桩目录，内容写 `26.0.0` | `Failed to determine Command Line Tools version from version.txt` |
| 反读 `dist/cli.js` 找解析正则 | `sS=/^#\s*Version:\s*(\S+)/` —— 必须写成 `# Version: 26.0.0` |
| 按正确格式重试 `create` | ✅ **成功**，30 个文件，`Template integrity check passed.` |
| 桩 CLT 下 `devecocli build` | ❌ `spawn <CLT>/tool/node/bin/node ENOENT` |
| `--api-level 24` | ❌ `Invalid API version 24. Your SDK supports API version 17-23` |

## 原始发现

### 一、`create` 不需要 SDK，`build` 需要

`devecocli create` 只做两件事：校验参数、把包内 `templates/application/`（25 个文件）
做变量替换后落盘。**它完全不碰 SDK。** 唯一门禁是 `DEVECO_CLI_CLT_PATH` 下有个可解析的 `version.txt`。

这条此前没意识到——一直把「CLT 未就位」理解成「什么都做不了」，
实际上「生成工程结构」这件事的依赖比想象中轻得多。

### 二、`build` 缺的东西很具体

```
[ohpm install] Running...
Command failed with ENOENT: <CLT>/tool/node/bin/node <CLT>/ohpm/bin/pm-cli.js install --all
```

即 CLT 里必须真有 `tool/node/bin/node` 与 `ohpm/bin/pm-cli.js`，之后还要 SDK 与 hvigor。
注意 ohpm 的位置是 `$CLT/ohpm/`，**不是** `$CLT/tool/ohpm/`。

### 三、API level 上限硬编码 23

`dist/cli.js` 的 `RI()` 函数：

```js
function RI(n,e){ let t = e?.getMaxApiLevel(), r = 23;
  if (n.apiLevel) { let o = Number(n.apiLevel);
    if (!Number.isInteger(o) || o < 17) throw ...'API version 17 or higher is required';
    if (t !== void 0) { if (o > t) throw ...`Your SDK supports API version 17-${t}` }
    else if (o > r) throw ...`Without DevEco Studio, supported range is API version 17-${r}`;
    return o }
  return t !== void 0 ? t : 23 }
```

下限硬编码 **17**，上限取 SDK 的 `getMaxApiLevel()`，取不到回落硬编码 **23**。
桩 CLT 下走的是第一条分支（`t` 有值且为 23），⚠️ 为什么桩也能让 `getMaxApiLevel()` 返回 23 未查清。

后果：工程现在是 `targetSdkVersion: "6.1.0(23)"`，而 `docs/01` 记的现网主力是 **6.1.1(24)**。
真 CLT 到位后要重新确认它带的 SDK 支持到哪一级。

### 四、一处旧记录修正

模板的 `hvigor/hvigor-config.json5` 与 `oh-package.json5` 的 `modelVersion` 实测是 **`6.1.0`**。
`harmony/README.md` 此前写的 `6.0.2` 有误，已改。

## 追加调研：不登录华为账号能不能编译？

结论：**能编出 HAP，但产物是 OpenHarmony HAP，不是 HarmonyOS NEXT HAP。**

这是本日最大的意外收获。此前默认「CLT 登录门禁 = 编译门禁」，实测不成立——
被登录挡住的只有 **HarmonyOS SDK 本体**，hvigor / ohpm / OpenHarmony SDK 三块全是公开直链。

### 三块拼图（下列 URL 与 sha256 为本会话亲自 `curl` 复核，非仅转述）

| 缺什么 | 免登录来源 | 实测 |
| --- | --- | --- |
| hvigor + ohpm 外壳 | `repo.huaweicloud.com/openharmony/compiler/hvigor/6.26.1/command-line-tools.zip` | 200，77,819,058 B，同目录 `.sha256` = `6db6883a6943649e1e84f155ef2151323e5e21ba3d2b7340fd1413bb0c756079` |
| `tool/node` | `repo.huaweicloud.com/nodejs/v22.14.0/node-v22.14.0-darwin-arm64.tar.gz` | 200，47,035,396 B |
| `sdk/` | `POST repo.harmonyos.com/sdkmanager/v5/ohos/getSdkList` | 200，21,331 B，**55 个组件、无鉴权**；API 23 = 6.1.0.32 的 5 个组件齐全 |

`getSdkList` 的请求体：`{"osType":"darwin","osArch":"arm64","supportVersion":"26.0-ohos-single-1"}`。
⚠️ `osType` 在 OpenHarmony 分支必须填 `darwin`（原值直传，填 `mac` → `139403 参数校验未通过`）；
HarmonyOS 分支反过来只认 `mac`。返回的每个组件都自带 `archive.url` + `size` + `checksum`，例如 ArkTS：

```json
{"path":"ets","apiVersion":"23","license":"OpenHarmony-SDK","version":"6.1.0.32",
 "displayName":"ArkTS","releaseType":"Release",
 "archive":{"url":"https://contentcenter-drcn.dbankcdn.cn/pub_1/.../8nF9GUKbS6eqma5qiqUiEQ.zip",
   "size":"73205166",
   "checksum":"5f3a2b813a6c540be806672b6a0e0699df221eec169fef5627dbe618a4ebb132","osArch":"arm64"}}
```

API 23 恰好对上工程现在的 `6.1.0(23)`，不用改版本号。

### 那个 `command-line-tools.zip` 就是完整 CLT 外壳

解包后正是 `$CLT` 期望的树，且 `sdk/` 与 `tool/node/` **是空占位**——正好是要填的两个洞：

```
version.txt   # Version: 26.0.0.461   ← 自带的就满足今天反读出的正则
bin/{codelinter,hstack,hvigorw,ohpm}
hvigor/bin/hvigorw.js      hvigor/hvigor/ @ohos/hvigor 6.26.1
ohpm/bin/pm-cli.js         ← 正是步 1 报 ENOENT 缺的那个文件
sdk/     ← 空
tool/node/ ← 空
```

`linux-x64` 标签是装饰性的：包内并行带各平台原生附件（`oxc-resolver/resolver.darwin-arm64.node` 等），macOS ARM 可用。
ohpm 默认仓库 `$CLT/ohpm/resources/.default-registry` = `https://ohpm.openharmony.cn/ohpm/`，免登录；
工程需要的 `@ohos/hypium`、`@ohos/hamock` 实测可取。
⚠️ 其 `.har` 对 `HEAD` 返回 401、对 `GET` 返回 302 → 200，**用 HEAD 探测会误判成需要鉴权**。

### 「攒一个假 HarmonyOS CLT」在哪里断掉

两个 SDK 家族由**元数据文件名**硬性区分，这是拦路点，不是配置问题：

| | OpenHarmony | HarmonyOS |
| --- | --- | --- |
| 元数据文件 | `oh-uni-package.json` | `sdk-pkg.json` |
| 允许的 metaVersion | `3.0.0` / `3.0.1` / `3.0.2` | `1.0.0` / `1.0.1` |

`runtimeOS` 只接受 `"OpenHarmony"` / `"HarmonyOS"`（否则 `INVALID_RUNTIME_OS_VALUE`），它决定加载器走哪一支。
走 HOS 支时找 `sdk-pkg.json`，OpenHarmony 包里没有；手工伪造也过不了 metaVersion 白名单。
**所以只能正当地走 OpenHarmony，不能伪装成 HarmonyOS。**

免登录拿 HarmonyOS SDK 的途径**未找到可信的**：HOS 的 `getSdkList`（v7）虽然也免鉴权可答，
但返回的 19 条全是模拟器系统镜像，没有 ets / toolchains；Docker Hub 无官方镜像；
三方 GitHub / 网盘转载**无法校验完整性**（官方未公布 HarmonyOS SDK 的 sha256），
且内含 JDK/Node/JAR 可执行文件会直接进入编译产物链路，**不采用、不记录 URL**。

### 签名不是障碍

toolchains 组件自带 `OpenHarmony.p12`、`OpenHarmonyProfileDebug.pem`、`UnsgnedDebugProfileTemplate.json`，
可产出已调试签名的 HAP，**不需要华为开发者证书**（也就不涉及实名认证）。
ArkWeb 主线也不受影响：API 23 的 ets 组件含完整 `@kit.ArkWeb.d.ts`、`component/web.d.ts`、
`@ohos.web.webview.d.ts`、`@ohos.web.netErrorList.d.ts`。

### 代价：一处工程配置改动，性质是换平台

`build-profile.json5` 的 `runtimeOS` 要从 `"HarmonyOS"` 改成 `"OpenHarmony"`。
这不是一个开关级改动——**产物的运行目标变了**，面向 OpenHarmony 设备/模拟器，
预期装不进 HarmonyOS NEXT 真机。所以这条路能兑现的是
「ArkTS/ArkUI/ArkWeb 代码被真编译器检验」，**不是**「HarmonyOS 基座跑起来」。

⚠️ 待核实（未实跑，一律不得宣称已验证）：

- hvigor 6.26.1 是否接受 `modelVersion: "6.1.0"`（schema 无 enum 约束，运行时未测）
- `runtimeOS: "OpenHarmony"` 下 `compatibleSdkVersion` 的确切字面量写法
- 产出的 HAP 能否装进 HarmonyOS NEXT 真机（预期：不能）
- `repo.huaweicloud.com/openharmony/os/` 两个整包解压后的完整层级（未下载，不凭印象补）

顺带修正 `harmony/env.sh` 里一处注释：`$CLT/sdk/default/openharmony/toolchains` 是
DevEco CLI 的 **`hdcPath`（设备部署用）**，不是构建期布局。构建期 OpenHarmony 的布局是
`$CLT/sdk/23/{ets,js,native,toolchains,previewer}`。

## 判断

- **「有工程」这件事真了。** `harmony/HybridShell/` 是 `devecocli create` 从官方模板生成的，
  不是手搓，CLI 自己打了完整性校验通过。这不违反 `CLAUDE.md` 的「不手搓」约定。
- **但用了一个桩，必须知情。** `~/.local/hmos-toolchain/clt-stub/` 里只有一个 `version.txt`，
  是为了骗过版本门禁。它**只对 `create` 有效**，对 `build` 无效——这是设计边界，不是配置问题。
  故意不叫 `command-line-tools`，免得和真 CLT 混掉。
- **「未编译验证」标注一条都不能摘。** 按 `CLAUDE.md`，摘标注的前提是真的过了 `devecocli build`。
  现在做的所有校验（JSON 解析、`node --check`、括号平衡）都不触及 ArkTS 语义与 ArkUI 规则。
  `code-linter` 同样要 CLT，所以连静态检查都没做上。
- **风险点：代码越多，未验证的存量越大。** 281 行 `Index.ets` 里每一条 W 规则的落地都是推演。
  真编译时大概率会暴露一批错误——这正是 `experiments/002` 想要的产出，但目前拿不到。
