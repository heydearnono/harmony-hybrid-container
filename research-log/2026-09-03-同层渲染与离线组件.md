## 关键发现

### 1. 「离线 Web 组件」确认**不是**「离线包」——昨天的怀疑是对的

`web-offline-mode` 讲的是**离屏预创建的 Web 组件**：用 `NodeContainer` + `NodeController` +
`BuilderNode` 命令式建出来但先不挂树，状态是 **Hidden + Inactive**，需要时再挂。
用途纯粹是性能优化（预启动渲染进程、预渲染页面），和 H5 离线资源打包**毫无关系**。

昨天在遗留里写的那句「注意『离线 Web 组件』**未必**等于『离线包』，别按字面理解」
拦住了一次可能的误写。这类「名字有歧义先标一笔」的动作值得保留。

真正的离线资源那条线在 `web-cross-origin` / `web-scheme-handler`（自用域名 + 拦截映射）。

### 2. 两个具体数字，比任何描述都有用

- **每个 `Web` 组件约占 200MB 内存**（官方原文「大约200MB」），并且官方另一页明写
  **「Web 内核对内存大小的申请无限制约束」**。两条放一起看，就理解了为什么官方反复说
  **每个窗口只用一个 `Web` 组件**、靠复用而不是多开。
- 同层渲染 vs `Stack` 堆叠，列表滑动单帧 `ReceiveVsync` 渲染耗时 **5ms → 1ms**。
  这是官方抓 Trace 的实测数字，是「该不该上同层渲染」最硬的判据。

### 3. 一条真正的能力互斥：同层渲染 ⊥ 同步渲染模式

- `web-render-mode`：`SYNC_RENDER` 的卖点是能渲染**超长**内容（上限 500,000px），
  而默认的 `ASYNC_RENDER` **超过 7,680px 物理像素直接白屏**。且**两者都不支持动态切换**。
- `web-same-layer` 的约束里有一条：**开启同层渲染后，该 `Web` 组件打开的所有页面都不支持 `SYNC_RENDER`。**

合起来就是一个架构级的二选一：**要么同层渲染，要么超长页面同步渲染，不能都要。**
两条信息分别写在两个页面里，单读任一页都发现不了。这条已作为 W19 记入 `docs/03`。

### 4. 同层渲染的坑几乎全是「视觉 bug」，一条编译错都没有

| 类型 | 具体 |
| --- | --- |
| 不生效 | `enableNativeEmbedMode` 默认关闭 → 页面显示「该插件不支持」 |
| 不识别 | `<embed>` 的 type 不以 `native/` 开头；`<object>` 未 `registerNativeEmbedRule` |
| 被拉伸 | 同层标签高度 > 8000px（GPU 纹理上限）；自定义组件最外层容器宽高 ≠ 标签宽高 |
| 错位 | `TextInput` 没用 `Stack` 包裹、`NodeContainer` 没和标签对齐 → 光标与文本选择框错位 |
| 静默降级 | `registerNativeEmbedRule('object','application/pdf')` 与 W3C 标准类型重合 → ArkWeb 走 W3C 行为 |

最后一条尤其阴：**注册成功了，但就是不当同层标签用。**

另外两条硬禁：不能拿 W3C 标准标签（`<input>`、`<video>`）当同层标签；
不能同时把 `<embed>` 和 `<object>` 都配成同层标签。

### 5. 「小程序容器」的答案变清楚了一半

昨天遗留写「官方只在简介里点了一句场景，是否有成套能力未确认」。
今天 `web-same-layer` 开篇给了具体做法：**小程序的地图组件用 `XComponent` 渲染以提升性能，
输入框组件用 `TextInput` 渲染以获得与系统一致的输入体验。**

判断：**官方没有「小程序容器」这个成品 Kit，路子是「ArkWeb + 同层渲染自己搭」。**
所以同层渲染不是可选优化，而是这个方向的必经能力。已按 🔶 部分确认写入 `docs/05`。

### 6. 进程模型里两条反直觉的默认行为

- **移动设备默认单渲染进程（省内存），2in1 默认多渲染进程（安全稳定）。** 默认值随设备变。
- ⚠️ `setRenderProcessMode` **传入不在 `RenderProcessMode` 枚举范围内的值 → 自动按多进程处理**。
  不是回落到「更省的单进程」，而是回落到多进程。传错值的后果是内存涨而不是行为退化。

配套的三条：`terminateRenderProcess()` 会影响**共享该进程的所有实例**；
共享进程时 `onRenderExited` 在**每个受影响的 Web 组件上各触发一次**；
`sharedRenderProcessToken` 是 **`Web` 组件的构造参数**（不是属性），同 token 优先复用同一渲染进程。

### 7. 「预启动渲染进程」的收益前提被官方写在小字里

`web-offline-mode` 原文：**仅在采用单渲染进程模式的应用中优化效果显著**；
且**渲染进程只有在所有 `Web` 组件都销毁后才终止**，故建议至少保持一个 Web 组件活着。

结合发现 6：移动设备默认就是单进程，所以这个优化在手机上默认可用；2in1 上要先改模式。

预渲染还有一个对本项目直接相关的限制：停止渲染的时机官方推荐用 `onFirstMeaningfulPaint`，
而这个接口**只适用 http/https 页面**。**本地 `$rawfile` 场景拿不到这个时机**——
`experiments/002` 走的正是 `$rawfile`，所以预渲染那套在最小基座里用不上，得另找停止时机。
