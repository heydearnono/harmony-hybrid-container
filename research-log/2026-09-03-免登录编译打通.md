### ⚠️ 体积比预估大 5 倍

原先按调研估的是「约 250 MB」，实际 **SDK 五组件合计 1,255 MB（解开后 4.0 GB）**：

| 组件 | 下载 |
| --- | --- |

| js | 56.4 MB |

`native`（NDK）与 `previewer` 本工程用不上——没有 C++ 模块、不用预览器——
**但 hvigor 仍然强制要求这两个组件在位**，缺了会报：

```
Error Code: 00308018 Unknown Error
Cause: The SDK license agreement is not accepted.
... re-download the Native:6.1.0.32,Previewer:6.1.0.32 SDK
```

这条报错**文本是误导的**：它不是真的许可证问题，而是「本地缺件 → 转去远端解析 → 远端件需先接受许可」。
读 `oh-sdk-info-handler.js` 的 `getOrDownload()` 可知本地已有的件不走许可检查。
所以正解是**把缺的件正当装上**，而不是去伪造 `$SDK/licenses/<id>.sha256`
（`AbstractLicenseManager.hasAccepted()` 就是比这个文件里的 hash）——
伪造等于代人接受许可协议，不做。

## 最有价值的一条：编译器真的在做类型检查，W1 由此转为实测

光看 `BUILD SUCCESSFUL` 不能排除「它只是转译、没查类型」。做了反向实验：
把 `sendToH5()` 里 W1 的正确写法故意改成错的，再编译。

```diff
- this.ports[1].postMessageEvent(JSON.stringify(payload));
+ this.ports[1].postMessage(JSON.stringify(payload));
```

```
ERROR: Failed :entry:default@CompileArkTS...
10505001 ArkTS Compiler Error
Error Message: Property 'postMessage' does not exist on type 'WebMessagePort'.
  At File: .../entry/src/main/ets/pages/Index.ets:177:21
COMPILE RESULT:FAIL {ERROR:2}
BUILD FAILED in 3 s 4 ms
```

**这是 W1 的机器证据**：`WebMessagePort` 上确实没有 `postMessage`，写错会在编译期被抓，
不是运行期静默失败。改回后重新 `devecocli build` 恢复 `BUILD SUCCESSFUL`，文件已还原。

推论：`Index.ets` 里其余靠 API 签名成立的规则（W5 的 `deleteJavaScriptRegister`、
W12 的 methodList 形参、W16 的静态方法归属、R2/R16 等）**同样过了类型检查**。
但 W2/W3/W4/W9/W10/W11/W15 是**运行期语义**，编译器管不着，仍然只有文档依据。

## 判断

- **「未编译验证」这个标注可以改写，但不能简单摘掉。** 准确说法是
  **「已过 OpenHarmony API 23 编译，未在 HarmonyOS SDK 上编译，未运行」**。
  OpenHarmony SDK 是子集，过了它不等于过 HarmonyOS SDK。
- **「AI 开发鸿蒙」的关键一环兑现了。** 此前所有代码都是推演，现在有了编译器这个裁判。
  281 行一次过（除了两处平台配置差异），说明 `docs/03` 的 R/W 规则集在类型层面是站得住的。
- **`code-linter` 仍然没有。** `$CLT/bin/codelinter` 只是个壳，包内没有 `$CLT/codelinter/`
  实体，报 `File not found`。静态检查这条线还是空的。
- **两处工程改动是平台差异，不是代码缺陷**，且都在文件里写了怎么改回去：
  `build-profile.json5` 的 `runtimeOS` / 三个版本号、`module.json5` 的 `deviceTypes`。
