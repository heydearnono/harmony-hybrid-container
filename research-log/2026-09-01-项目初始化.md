## 检索路径与原始发现

### 一、官方文档不可直接抓取（已解决）

- `WebFetch https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/ai-overview` → 只拿到搜索框、「智能客服」「合作咨询」等外壳文案，正文为空，判定为 JS 动态渲染。
- `curl` 同一 URL → HTTP 200，**size=1796 字节**，`<body>` 里只有 `文档中心` 四个字。确认是 Angular SPA。
- 试 `<link rel="alternate" type="text/markdown">` 暗示的 `.md` 后缀（`.../core-speech-kit-api.md`）→ 404。
- 试 OpenHarmony 文档镜像取巧：`gitee.com/api/v5/repos/openharmony/docs/...` 连接超时；`raw.githubusercontent.com/openharmony/docs/...` 404 + GitHub API 限流。且 OpenHarmony 文档不覆盖 Core Speech / Core Vision 这类 HarmonyOS 闭源 Kit，方向本身也不对。
- 搜索引擎同样读不到正文：搜 `Core Speech Kit 开发指南 developer.huawei.com/...` 返回的官方链接全是空 snippet，只有社区转述文章（dev.to、腾讯云社区）有内容——这些只能当线索。
- 转而反查前端 bundle：`main.38ef39de8d22e671.js` 里发现 `ruleURL("/cn/documentPortal/getCatalogTree")` 等 11 个端点；`assets/const/official/env.*.js` 里拿到基址 `https://svc-drcn.developer.huawei.com/community/servlet`。
- **用空 body POST 探参数**最省时间：接口把校验错误原样报回，例如
  `getDocumentById.req.objectId:must not be blank`、`getCatalogTree.req.showHide:Enumeration is invalid`。
- 关键坑：`getDocumentById` 的 `objectId` **不是**目录树里的 `nodeId`（传 nodeId 报 `92531031 document not found`），而是 URL 末段的 slug（如 `core-speech-introduction`）。
- 实测通过：`getCatalogTree` 返回开发指南全量目录树（1,261,756 字节 JSON）；`getDocumentById` 返回正文 HTML + 元信息（`version=V233`、`updatedDate=2026-08-31 17:49:42`、`versionLabels=["hmos-503"]`）。

→ 固化为 `tools/hwdoc.py`，方法写入 `docs/00-doc-retrieval.md`。

### 三、Core Speech Kit 抽样验证（证明通道可用）

读 `core-speech-introduction` 正文，官方原文摘录：

> Core Speech Kit（基础语音服务）集成了语音类基础AI能力，包括文本转语音（TextToSpeech）及语音识别（SpeechRecognizer）能力。

> 文本转语音：将一段不超过10000字符数的文本合成为语音并进行播报。
> 语音识别：将一段音频信息（短语音模式不超过60s，长语音模式不超过8h）转换为文本。

> 支持的设备：Phone、Tablet、PC/2in1。
> 仅适用于中国境内（香港特别行政区、澳门特别行政区、中国台湾除外）。
> 语音识别支持的模型类型：离线。

这类「地区限制」「设备限制」是纯凭模型记忆几乎不可能写对的信息，也印证了 CLAUDE.md 事实纪律的必要性。

## 判断

- 官方文档通道打通后，本仓库的事实质量瓶颈从「查不到」变成「读多少」。社区文章降级为纯线索，不再作为结论依据。
- 端侧 AI 有清晰的两层结构：`Core Xxx Kit`（原子能力）与 `Xxx Kit`（场景化/控件级），另有三套推理运行时（MindSpore Lite / Neural Network Runtime / CANN）承接自带模型的场景。这个分层是 `docs/02-ondevice-ai-map.md` 的骨架。
- `hwdoc.py doc` 返回的 `updatedDate` 让「事实带时效」这条纪律可以自动化：每条来源都能记下文档自身的更新时间，而不只是我的访问时间。

### 修正一：`hmos-503` 不是版本标签（上面「遗留」第 1 条作废）

对内容版本各异的 `overview-2600` / `overview-611` / `overview-500` / `development-intro-api` 等页面交叉验证，`versionLabels` 返回值恒为 `hmos-503`，判定为站点常量，**不能用来判断文档对应的 HarmonyOS 版本**。判断版本只能看正文与 `updatedDate`。已同步修正 `docs/00-doc-retrieval.md`。

这条值得记一笔：它是本轮唯一一个「我先给出了猜测、后被证伪」的事实。猜测当时已标 ⚠️ 待核实，纪律起了作用。

### 修正二：「API Level」已不是当前官方措辞

26.0.0 起 API 版本号改为纯 SemVer `X.Y.Z`；26.0.0 之前写作 `X.Y.Z(N)`，括号里的 N 才是 OpenHarmony 底座的 API level。本仓库统一改用「起始版本」并保留官方原格式。上文各处「API Level」的说法按此理解。

### 补充：第三个可用文档目录

`getNavigationAddress` 探到 `harmonyos-releases`（版本说明与兼容性），是版本号、现网设备分布、兼容性影响因素的一手来源。另：`AppGallery-Connect` 目录 `getCatalogTree` 返回空树，AGC 自有文档区不在此通道内。

### 本轮最有价值的三个发现

1. **DevEco CLI 官方定位就是给各类 AI Agent 用**（原文点名 Cursor、OpenCode），`npm i -g @deveco/deveco-cli`，支持 macOS，并提供 MCP server 与 `init --mcp|--skill` 注册。DevEco Code 则基于开源 OpenCode + 华为 BitFun 构建。——本项目的正题上，官方已经先走了一步。
2. **本机的卡点不是 IDE，是 Command Line Tools + JDK**。官方明确 Hvigor 可独立于 DevEco Studio 运行，命令行构建在 macOS/Linux 无差异。因此「无工具链」这个前提本身可能是错的，已立 `experiments/001` 验证。
3. **Core Vision Kit 的 8 个能力，官方从未承诺端侧或离线**。16 篇正文零标注。此前「端侧原生 AI 能力」这个调研方向里，至少视觉这一支的「端侧」是我们自己加的假设。

### 官方文档自身的矛盾（已在各文档留档，不做取舍）

- NNRt 简介写「目前仅支持同步推理」，但 `neural_network_core.h` 有 `OH_NNExecutor_RunAsync` / `OH_NNExecutor_SetOnRunDone`。
- CANN Kit 约束写「仅适用于带 Kirin NPU 的设备」，异构一节写「没有 NPU 时也能通过 CPU 提供更广泛的硬件适应能力」。
- 26.0.0 发布日期：`overview-allversion` 写 2026/08/28，`overview-2600` 正文写「8月29日正式Release发布」。
- Core Speech 错误码 `1002300007` 出现在示例注释里，错误码清单与 `speak` 错误码表均无此条。
- Intents Kit 指南标题写 `AgentAbilityExtension`，实际类名是 `AgentExtensionAbility`；A2A 示例里出现 Python 风格关键字参数 `want=want`。

## 当日追加（二）：ArkTS 规则清单回收，K 系列并入

`docs/03-arkts-codegen-rules.md` 成稿：**21 条语言/工程规则（R1–R21）**，每条可追到官方 slug。另把并行调研中攒下的 **12 条端侧 AI Kit 调用陷阱并入为 K1–K12**，与 R 系列分节，理由是两者失败模式不同——R 系列编译期就报错，K 系列**多数不会编译失败，而是运行时静默失效或行为与直觉相反**，对 AI 生成代码危害更大。

最该记住的几条：

- `online: 1` 的语义是**离线**（K2）。这种反直觉的取值设计，模型不可能靠推理写对。
- 不调 `setListener` → 一个回调都不来，也不抛异常（K4）。
- TTS 实例上限 3 是**设备级、跨应用共享**的配额（K5），不是应用内配额。
- Core Vision 一个 Kit 里两套互不兼容的 API 风格，且**都不能 `new`**（K6）。
- R2「类型必须显式」是 AI 写 ArkTS 最高频的编译错误来源（10605038 / 10605090 / 10605034）。
- R8「导入路径用 `@kit.XxxKit`」——参考页标题写的 `@ohos.*` 是**模块名**，不是应写进代码的路径。

同时把 4 条新条目补进「常见幻觉清单」：`Core Natural Language Kit` 这个 Kit 名、`new XxxAnalyzer()`、二维码归属、以及原有的组件名与大写 `AppStorage.Get`。清单口径统一为**只说「官方文档中检索不到」，不断言其不存在**。

### 这轮暴露的一个证据缺口

R8 的总纲页《导入HarmonyOS SDK的开放能力》**在两棵目录树里都检索不到**（`import-sdk` / `sdk-import` / `import-capabilities` / `development-intro-import` / `kit-import` 全部 `92531031 document not found`）。`development-intro-api` 正文明确引用了它，说明页面存在但不在本通道可达的目录内。

后果：「是否所有 Kit 都走 `@kit.*`」「`@ohos.*` 在 ArkTS 中是否仍有效」只有各模块「导入模块」小节这一级证据，未获总纲确认，已在文档标 ⚠️。这也是 `hwdoc.py` 通道的第二个已知盲区（第一个是截图）。
