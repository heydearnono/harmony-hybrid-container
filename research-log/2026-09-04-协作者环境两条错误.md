# 2026-09-04 别人下载后打不开：平台配置、hvigor 版本、syscap 三道坎

## 问题

代码推到 `origin/main` 之后，协作者在自己机器上先后报了四条错：

1. `Select an OpenHarmony or HarmonyOS project`
2. `The ArkTS SDK of version 23 in OpenHarmony is not found.[entry]`
3. `00303028 Unsupported modelVersion of Hvigor 6.1.0`（支持的是 6.0.1）
4. `00401004` 设备缺 15 条 syscap，装不上

要回答的是：各自的成因是什么，仓库该怎么改才能让别人下载后直接可用。

## 第一条：`Select an OpenHarmony or HarmonyOS project`

**成因是我自己的流程失误，不是工程结构问题。** 我上一轮把 33 个工程文件提交在
本地分支 `feat/openharmony-build-passing` 上就没再管，`origin/main` 停在 `09d6227`，
它的 `harmony/` 下只有 `README.md` 和 `env.sh`。核对方式：

```sh
git ls-tree -r --name-only origin/main | grep -c 'harmony/HybridShell'   # → 0
```

协作者下载到的确实是个没有工程的目录，IDE 报「请选择一个工程」完全正确。

⚠️ 我第一次回答把「打开的目录层级不对」排在最可能，**判断错了**，是用户提出
「是不是没提交代码」才查出真相。**教训**：交付给别人用的东西，要以远端内容为判据
（`git ls-tree origin/main`），不能以「我本地 commit 过了」为判据。

合并推送后（`09d6227..5df86bf`）远端已含全部 33 个文件，第一条消失。

## 第二条：`The ArkTS SDK of version 23 in OpenHarmony is not found.[entry]`

### 检索路径

先确认这句话是不是我这条链报出来的：

```sh
grep -rlo "ArkTS SDK of version" ~/.local/hmos-toolchain/clt-oh/     # 无匹配
grep -rho "SDK of version[^\"'\`]\{0,80\}" ~/.local/hmos-toolchain/clt-oh/   # 空
```

`clt-oh` 里唯一含 "ArkTS SDK." 的是一条无关的 Kit 配置报错
（`sdk/23/ets/build-tools/ets-loader/lib/process_kit_import.js` 的
`Kit '${t}' has no corresponding config file in ArkTS SDK.`）。
所以**这句不是本机 OpenHarmony 链发出的，来自协作者那侧的 HarmonyOS hvigor / DevEco Studio**。

### 原始发现：反向实验拿到镜像错误

把工程切回 HarmonyOS 配置（`runtimeOS: "HarmonyOS"` + `"6.1.0(23)"`），
用本机只有 OpenHarmony SDK 的链去编译：

```
> hvigor ERROR: 00303168 Configuration Error
Error Message: SDK component missing.
* Try the following:
  > Please verify the integrity of your SDK.
> hvigor ERROR: BUILD FAILED in 666 ms
hvigor sync failed
```

两条错误**互为镜像**：

| 工程写的 | 机器上有的 SDK | 报什么 |
| --- | --- | --- |
| `runtimeOS: "OpenHarmony"` + `23` | 只有 HarmonyOS SDK | `The ArkTS SDK of version 23 in OpenHarmony is not found.[entry]`（协作者侧） |
| `runtimeOS: "HarmonyOS"` + `"6.1.0(23)"` | 只有 OpenHarmony SDK | `00303168 SDK component missing`（本机实测，2026-09-04） |

### 判断

成因确定：`5df86bf` 提交的是**为了本机免登录编译而改过的 OpenHarmony 配置**
（`runtimeOS: "OpenHarmony"`、三个版本号是整数 `23`、多一个 `compileSdkVersion`、
`deviceTypes: ["default"]`）。协作者用 DevEco Studio for HarmonyOS，装的是 HarmonyOS SDK，
按 `runtimeOS` 去找 OpenHarmony 的 ets SDK，找不到。

这印证了 2026-09-03 记的那条边界：两套 SDK 家族靠元数据文件名硬性区分，**不能互相顶替**。
让协作者去装 OpenHarmony SDK 23（1,255 MB）不是好方案——DevEco Studio for HarmonyOS
是否提供该 SDK 也未确认（⚠️ 待核实）。

## 第三条：`00303028 Unsupported modelVersion of Hvigor 6.1.0`

对方日志的命令行是 `/Applications/DevEco-Studio.app/Contents/tools/hvigor/bin/hvigorw.js`，
说明这次是 DevEco Studio 自己的 hvigor 在跑（本机 `/Applications/DevEco-Studio.app` 不存在，已核）。
它自报 `The supported Hvigor modelVersion is 6.0.1`，而工程两处写着 `6.1.0`：

- `hvigor/hvigor-config.json5:2`
- `oh-package.json5:2`

两处都是 `devecocli create`（DevEco CLI 1.3.0-stable）落盘时写进去的，本机 hvigor 是 6.26.1，认 6.1.0。
**即对方的 Studio 比生成这个工程的 CLI 老一档。**

判断：优先升 Studio，而不是把工程 `modelVersion` 降到 6.0.1 —— 工程还锁着
`compatibleSdkVersion: "6.1.0(23)"`，只认 model 6.0.1 的 Studio 大概率也没有 API 23 SDK，
降 modelVersion 只是把报错往后挪一格。⚠️ 哪个 Studio 版本带支持 6.1.0 的 hvigor，未查到可信来源。

## 第四条：`00401004` 设备缺 15 条 syscap

报缺的是 `Telephony.{CoreService,CellularData,CallManager,SmsMms,StateRegistry}`、
`Communication.{Bluetooth.Core,WiFi.P2P,FusionConnectivity.Core}`、
`DistributedDataManager.{KVStore.Core,DataObject.DistributedObject}`、
`DistributedHardware.DeviceManager`、`Multimedia.{Media.AVTranscoder,Drm.Core}`、
`BundleManager.AppDomainVerify`、`Customization.EnterpriseDeviceManager`。

这个工程只用 ArkWeb，一条都没 import。为什么会要求它们？读 hvigor 6.26.1 的实现：

```
hvigor/hvigor-ohos-plugin/src/tasks/syscap-transform.js
  → deviceTypes = module.json5 的 deviceTypes
hvigor/hvigor-ohos-plugin/src/tasks/abstract/abstract-syscap-transform.js
  → getIntersectedGeneralSysCapSet(deviceTypes)
     取 sdk/23/ets/api/device-define/<type>.json 的 SysCaps 求交
  → 写 intermediates/syscap/default/rpcid.{sc,json}
```

**要求的 syscap 全集来自 `deviceTypes`，与代码 import 了什么无关。** 本机产物实测：

```
rpcid.json: {"api_version": 23, "syscap": [...]}  →  227 条
协作者报缺的 15 条，227 条里全都在（15/15）
```

各设备类型的 SysCaps 条数：`default` 227、`2in1` 223、`tablet` 219、`wearable` 193、
`tv` 181、`liteWearable` 17。`Telephony.*` 只有 `default` 和 `wearable` 有；
而缺失清单里既有 Telephony 又有几乎所有类型都有的 Bluetooth/WiFi.P2P/KVStore/DRM
—— 说明**目标设备的能力集比任何一个完整设备类型都小，最可能是模拟器**（⚠️ 未向对方确认）。

### 收窄办法（OpenHarmony 侧已实测）

`abstract-syscap-transform.js` 里有这么一段：

```js
processProductionSysCap(t,e){
  const s=t.addedSysCaps;   s&&s.forEach(t=>{e.add(t)});
  const o=t.removedSysCaps; o&&o.forEach(t=>{e.delete(t)})
}
```

它读的是模块源码根的 `syscap.json`（`CommonConst.SYSCAP_JSON="syscap.json"`），
schema 是 `{devices:{general:[],custom:[]}, production:{addedSysCaps:[],removedSysCaps:[]}}`，
删除发生在写 rpcid 之前。于是加了 `entry/src/main/syscap.json`，把那 15 条列进 `removedSysCaps`：

| 指标 | 加之前 | 加之后 |
| --- | --- | --- |
| `rpcid.json` 条数 | 227 | **212** |
| 那 15 条 | 全在 | 全部删除 |
| `SystemCapability.Web.Webview.Core` | 在 | **仍在** |
| 编译 | `BUILD SUCCESSFUL` | `BUILD SUCCESSFUL in 4 s 87 ms` |

⚠️ **但 `doTaskAction()` 第一行是 `if (this.targetData.isHarmonyOS()) return;`** ——
这条 OpenHarmony 链在 HarmonyOS 目标下压根不跑这个 task。
所以 `syscap.json` 对协作者那侧（HarmonyOS + DevEco Studio）**是否生效未核实**，
要他们实际装一次才知道。

## 落点


新增 `harmony/switch-runtime.sh`，把两个文件四处值的切换收成一条命令：

```sh
bash harmony/switch-runtime.sh          # 看当前在哪一侧
bash harmony/switch-runtime.sh ohos     # 本机编译前切
bash harmony/switch-runtime.sh hos      # 提交前切回（仓库默认）
```

实现上把两个文件的平台相关行包进 `>>> PLATFORM BLOCK >>>` / `<<< PLATFORM BLOCK <<<`
标记，脚本只重写标记之间的内容（python3 正则，注释与其余配置原样保留）；
标记丢了就报错退出，而不是猜着改。

**仓库默认值改成 HarmonyOS 侧**（= `devecocli create` 的原值），这样别人 clone 下来
用 DevEco Studio 能直接打开。代价要说清楚：**入库那一份配置本身没被编译器验过**，
本机没有 HarmonyOS SDK；跑通 `BUILD SUCCESSFUL` 的是 `ohos` 那一侧。

两侧都实测过一遍：`ohos` → `BUILD SUCCESSFUL in 3 s 399 ms`；`hos` → `00303168`（预期失败）。

改的文件：`harmony/switch-runtime.sh`（新）、`harmony/HybridShell/build-profile.json5`、
`harmony/HybridShell/entry/src/main/module.json5`、`harmony/README.md`（文首加平台配置一节、
`modelVersion` 归因修正）。

第四条另加：`harmony/HybridShell/entry/src/main/syscap.json`（新）、
`docs/03-arkts-codegen-rules.md` 新增 **R22**（`deviceTypes` → rpcid syscap 全集 → 00401004）。
