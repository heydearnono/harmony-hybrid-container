# 2026-09-02 ArkWeb 与混合容器：第一轮文档地图

## 问题

方向转向混合容器后，第一件事是把官方文档地图和几个核心 API 的**准确名称**拿到手。
按 `CLAUDE.md` 的事实纪律，原生 ↔ H5 通信这类 API 名最容易凭印象写错，必须逐条落到抓下来的正文。

## 检索路径

先起了个子 Agent 去跑 `tools/hwdoc.py`，**它在 600 秒无进展后被判定 stalled 失败**，
只回了一句「Rich doc map found」。所以改为自己直接跑，反而更快：

```bash
python3 tools/hwdoc.py tree harmonyos-guides ArkWeb    # 一次拿到整棵子树，约 60 个 slug
python3 tools/hwdoc.py doc <slug>                      # 逐篇抓正文到 /tmp/arkweb/
```

已抓并读过的 7 篇：`web-component-overview`、`web-in-app-frontend-page-function-invoking`、
`web-in-page-app-function-invoking`（928 行，用 grep 定位关键段）、`web-app-page-data-channel`、
`web-cross-origin`、`web-scheme-handler`、`web-resource-interception-request-mgmt`。
另抓未读：`web-offline-mode`（772 行）、`web_component_process`。

顺带一个操作坑：本机 zsh **没有 `timeout` 命令**（`(eval):1: command not found: timeout`），
给 `hwdoc.py` 加超时得靠工具自身的 timeout 参数。

## 关键发现

### 1. ArkWeb 支持模拟器 —— 这条改变了验证策略

`web-component-overview` 明确写「本 Kit 支持模拟器」。对比第一轮的端侧 AI：
K1–K12 那些行为型陷阱**全部只能在真机上验**（真机要实名认证 + AGC 签名）。

**即混合容器方向是可验证的，不必等真机。** 本机 macOS ARM 正是模拟器支持的两个平台之一。
这是方向转换的一个意外红利，也意味着 CLT 一到位，W 系列陷阱应当优先去实测而不是继续读文档。

### 2. 内核就是 Chromium，且要按内核版本判断特性支持

| 系统版本 | Chromium |
| --- | --- |
| 4.0 及之前 | M99 |
| 4.1 – 5.1 | M114 |
| 6.0 | M132 默认 / M114 可选 |
| 6.1 | M132 |
| 7.0 | M144 默认 / M132 可选 |

官方的口径是让开发者拿内核版本去 MDN / webassembly.org 查 W3C 支持情况。
结合 `docs/01` 的现网分布（6.1.1(24) 占 84.93%），**实际要兼容的主力内核是 M132**，不是 M144。

### 3. 通信是三条路径，各自还有 C/C++ 版

不是一个「JSBridge」，而是三族接口：`runJavaScript`/`runJavaScriptExt`（应用→前端）、
`javaScriptProxy`/`registerJavaScriptProxy`（前端→应用）、`createWebMessagePorts`（双向端口）。
每条另有 NDK 版本（`arkweb-ndk-jsbridge`、`arkweb-ndk-page-data-channel`）——这一层原先没预期到。

### 4. 消息端口的三个坑，全在官方示例里明摆着

- **两侧方法名不对称**：ArkTS 侧 `onMessageEvent` / `postMessageEvent`，H5 侧 `onmessage` / `postMessage`。
- **同一份代码里两个 `postMessage` 语义不同**：`controller.postMessage(name, ports, uri)` 是送端口，
  `port.postMessageEvent(data)` 才是发数据。
- **`WebMessage` 只收 `string` / `ArrayBuffer`**，传对象要 `JSON.stringify`。
  官方 FAQ 把「H5 发消息应用侧收不到」的第一原因就归给它。

这三条都是**静默失效**，不报编译错。正好是这个仓库最该记的那类东西。

### 5. 加载本地 H5 默认就被 CORS 拦死

`web-cross-origin`：ArkWeb 内核**禁止 `file` 与 `resource` 协议跨域**。
报错里的白名单是 `http, arkweb, data, chrome-extension, chrome, https, chrome-untrusted`
——**没有 `file` 和 `resource`**，但有个自定义的 `arkweb`。

所以「`$rawfile` 加载 index.html，里面的 js/css 全加载不出来」是设计行为。
两条解法：编自用域名 + `onInterceptRequest` 映射；或 `setPathAllowingUniversalAccess()` 白名单
（官方自己标为**高风险**，且路径含 `cache/web` 直接抛 401）。

### 6. 拦截有两套机制，能力不等价

`onInterceptRequest` **拿不到 Post Data**；`SchemeHandler` 能拿到、还能覆盖 ServiceWorker 的请求，
但必须在请求结束回调里清资源否则泄漏。选型判据：只做离线包映射用前者，要读 POST 体用后者。

### 7. 元服务不能用 `Web` 组件

要用 **ASCF Webview** 或 **AtomicServiceEnhancedWeb**。⚠️ 这两个组件还没查。

## 判断

- 混合容器的文档质量明显好于端侧 AI：指南页带完整可运行示例和 FAQ，`web-app-page-data-channel`
  的两条 FAQ 直接就是两条陷阱。**读示例代码比读描述性文字信息量大得多。**
- 一个系统性缺口：**指南页几乎不写起始版本。** W1–W8 里只有一条有版本号
  （`setPathAllowingUniversalAccess` 支持 `cacheDir`/`tempDir` 从 API version 21 起）。
  要准确版本必须去 `harmonyos-references` 查 `@ohos.web.webview`。这是下一轮该补的。
- 子 Agent 失败这件事的教训：**这类「跑固定脚本 + 逐篇抓取」的任务不适合外包**，
  自己串行跑一遍反而快且可控，因为每一步的输出都要当场判读。

## 当日追加：起始版本缺口已补，并且 API 参考页里又挖出 8 条陷阱

上面「遗留」第一条（起始版本全缺）已解决。做法是转到 `harmonyos-references`：

```bash
python3 tools/hwdoc.py tree harmonyos-references webview     # 入口 js-apis-webview，下挂约 40 个类/接口页
python3 tools/hwdoc.py doc arkts-apis-webview                # 模块描述，111 行
python3 tools/hwdoc.py doc arkts-apis-webview-webmessageport  # 628 行
python3 tools/hwdoc.py doc arkts-apis-webview-webviewcontroller  # 14178 行，靠 grep 定位方法头
```

### 版本口径找到了

模块描述页原话：「本模块**首批接口从 API version 9 开始支持**。后续版本如有新增内容，
则采用上角标单独标记该内容的起始版本。」

这条一句话就把整个查法定下来了：**API 参考页的方法标题上没有上角标就是 API 9**。
`grep -n '^#\+ 方法名'` 直接就能读出版本，因为上角标被 `hwdoc.py` 转成了文本后缀：

```
1179:#### refresh24+
1852:#### runJavaScriptExt10+
10561:#### setPathAllowingUniversalAccess12+
11595:#### setWebDebuggingAccess20+
```

两处**参数级**的版本差异是纯读指南页绝对看不到的：

- `runJavaScriptExt` 本身是 **10+**，但它的 `script` 参数收 `ArrayBuffer` 是**从 12 起**。
  即在 API 10/11 上 `runJavaScriptExt` 只能传 `string`。
- `createWebMessagePorts()` 是 9，但参数 `isExtentionType` 是 **10+**。

### 意外收获：API 参考页的信息密度远高于指南页

原本只是去补版本号，结果挖出 8 条新陷阱（W9–W16），指南页一条都没写：

| 新规则 | 一句话 |
| --- | --- |
| W9 | **`postMessageEvent` 之前必须先 `onMessageEvent`**，否则发送失败（17100010） |
| W10 | **前端传到应用侧的 `string` 被视为 JSON 数据，要 `JSON.parse`** |
| W11 | `runJavaScriptExt` **必须在 `loadUrl` 完成后**调（官方点名 `onPageEnd`） |
| W12 | 同步/异步方法列表**不可同时为空**否则注册失败；同一方法在两个列表里重复注册**默认走异步**；异步无返回值且顺序不保证 |
| W13 | 注册的对象**暴露给所有 page frames**，官方要求只在可信 URL / HTTPS 下注册 |
| W14 | **跨导航后 `runJavaScript` 的 JS 状态不保留**，要跨页保持得改用 `registerJavaScriptProxy` |
| W15 | controller 未绑定 `Web` 组件就调方法 → 17100001 |
| W16 | `setWebDebuggingAccess` 官方带安全提示「不建议在正式发布版启用」；带 `port` 的无线调试是 20+ 且 `port` 必须 > 1024 |

顺带修正了 W3：`WebMessage` 只收 `string`/`ArrayBuffer` **只是基础协议的限制**。
还有一套扩展协议 `postMessageEventExt` / `onMessageEventExt`（10+，载体 `WebMessageExt`）支持更丰富类型。
原来那条写法虽不算错，但会让人以为端口通道天生传不了复杂数据。

### 一条需要留意的口径冲突

`arkts-apis-webview` 模块描述页写「**示例效果请以真机运行为准**」，
而指南页 `web-component-overview` 写「本 Kit 支持模拟器」。

两者不直接矛盾（一个讲效果准确性、一个讲可运行性），但**具体哪些能力在模拟器上有差异官方没说**。
`experiments/002` 的风险要按这个调整——模拟器能跑通不等于真机表现一致。

### 判断

- **补版本号这件事的收益远超预期。** 目标是填 15 个版本号，结果拿到 8 条新陷阱、
  2 处参数级版本差异、4 个错误码。**指南页教「怎么用」，API 参考页才写「什么情况下会失败」**，
  而本仓库要的正是后者。这条方法论应固化：`docs/` 写某个能力时，指南页与 API 参考页都要过一遍。
- W 系列从 8 条涨到 16 条，且**全部有 slug 出处**，没有一条是凭印象。
